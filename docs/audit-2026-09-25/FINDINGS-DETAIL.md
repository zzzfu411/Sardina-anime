# 已修复的解析可用性问题

状态：已修复。严重性：Medium（P2）。审查基线：`95dccdd`；当前工作区已应用修复。

## 数据路径与前提

`AniChSource.search` 在 `packages/engine/src/sources/anich.ts:154` 从固定来源读取受限长度的响应，然后在 `:158` 传给 `decodeAniPage`。该函数的 `:75` 调用 `decodeAniCards → protoItems → decodeFields`，`:77` 再读取 envelope 游标。原 `decodeFields` 在每个重复字段处复制之前的整个数组，见 [不可变基线快照](protobuf-before.txt) 第 37 行；当前源码第 37–39 行已经改为追加。

输入必须来自配置中的 AniCh 上游；任意网页无法选择替代主机。攻击条件是该上游被控制或污染、AniCh 已启用，用户随后请求它的搜索或索引，并因缓存未命中或显式刷新实际读取上游。没有认证绕过、文件泄露或持久化改动证据。

## 本地证据

完全使用内存样本：100000 个空 field-1 记录，总长 200000 字节，未超过 100000 字段或 8 MiB HTTP 限制。原实现单次解析 16007.96 ms；另一个审查者经真实 `AniChSource.search` 与假 HTTP 对 2000/4000/8000/16000 字段分别测得 6.8/12.1/47.4/265.5 ms，预先安排的零延时定时器同样推迟。同步解析不能被超时信号中途抢占，因此会影响同进程 API 和媒体转发。

当前实现上限样本单次为 63.45 ms，见 [测量文件](parser-performance.json)。`tests/parsers.test.ts` 同时检查上限样本处理时间、解码结果和超限拒绝。未对任何真实来源发送测试输入。

## 修复与比较边界

将每次复制改成已有数组的 `push`，保留数量限制和损坏输入检查。FreeTube 仅作为单用户桌面媒体应用的部署基准；没有证据说明它使用相同解析器，所以不推断它有相同问题，也不借此降低本问题的确认程度。
